# 文档C：情报网设计 v1

> Serenity 2.0 第1阶段 | 2026-07-22
> 目标：建立可信、可度量、有时效的信息采集和验证体系

---

## 1. 目标与边界

### 目标

让Serenity在开盘前、盘中、盘后三个时段，都能获取并理解对持仓有影响的信息。不是"看更多新闻"，而是"只看对你有用的信息"。

### 边界

| 纳入 | 不纳入 |
|:----|:------|
| 持仓股公告、异动、新闻 | 宏观经济学预测 |
| 候选池关键事件 | 社交平台情绪（未验证前） |
| 行业/概念板块政策 | 付费研报摘要（无来源等级） |
| 主要指数与外围市场 | 临时蹭热点的财经自媒体 |
| A股交易规则变更 | 盘后数据挖掘（当日来不及用） |

### 三时段覆盖

| 时段 | 信息重心 | 推送方式 |
|:----|:--------|:--------|
| 盘前 06:00-09:00 | 隔夜外围、公告、停复牌、除权除息 | 开盘简报 |
| 盘中 09:30-15:00 | 持仓量价异常、板块涨跌、突发事件 | P0立即/P1按规则 |
| 盘后 15:00- | 收盘数据、因子更新、公告补充 | 收盘速览 |

## 4. 来源冲突处理原则

| 场景 | 处理 |
|:----|:-----|
| S级与A级冲突 | 以S级为准 |
| A级与B级冲突 | 以A级为准，记录冲突日志 |
| B级之间冲突 | 取发布时间更早的，双方来源都标注 |
| C级单独出现 | 标记"未核实"，不进入信号判断 |
| 同一时间3个异源确认同一事 | 置信度升级（无论等级） |

**核心规则**：无法确认的信息标记"待核实"，不得伪装成确定事实。

## 5. 信息采集与标准化

### 5.1 采集流程

```
定时轮询 (cron)
  ↓
各源独立采集 → 写入原始数据缓冲区
  ↓
数据清洗 → 去除HTML标签、去重、统一编码
  ↓
格式标准化 → 转为统一事件格式
  ↓
时效性检查 → 标记过期或重复信息
  ↓
源交叉验证 → 多源核对
  ↓
影响评估 → 映射到标的和账户
  ↓
进入情报队列等待推送
```

### 5.2 去重规则

- 同一事件在30分钟内被多个源报道 → 只推送一次，带多来源标签
- 不同源报道同一事件的同一侧面 → 合并为一条情报
- 同一公告在不同网站出现 → 以原始公告来源（S级）为准
- 旧消息重新传播（如1周前的分析文章被重发）→ 标记为"旧闻重发"并降低优先级

## 6. 多源验证与冲突处理

### 6.1 验证流程（三阶段）

```
Stage 1 - 自我验证（采集阶段）
  ├─ 数据格式校验：数值类型正确、时间戳合理
  ├─ 边界检查：涨跌幅<=10%（股票正常交易范围）
  └─ 数据完整性检查：字段不缺失

Stage 2 - 交叉验证（多源阶段）
  ├─ 2个源以上确认同一事件 → 可信
  ├─ 仅1个源报告 → 降低置信级，标记需要第2源确认
  └─ 各源报告不一致 → 以S/A等级高者为准，记录冲突

Stage 3 - 时序验证（时效阶段）
  ├─ 事件时间 vs 采集时间 vs 当前时间
  ├─ 计算延迟：publish_time - event_time
  └─ 计算滞后：current_time - publish_time
```

### 6.2 验证状态标记

| 状态 | 含义 | 能否触发信号 |
|:----|:-----|:-----------:|
| verified | 经过Stage1+Stage2验证 | ✅ 可|
| self_verified | 仅Stage1通过 | ⚠️ 仅P2/P3 |
| contradicting | 多源冲突 | ❌ 不可 |
| pending_verification | 待第2源确认 | ❌ 不可 |
| outdated | 超过有效期 | ❌ 不可 |

## 7. 时效性与失效机制

### 7.1 每条情报必须记录的时间戳

| 时间戳 | 含义 | 获取方式 |
|:-------|:-----|:--------|
| event_time | 事件真正发生时间 | 从原文解析 |
| publish_time | 来源首次发布时间 | 从元数据获取 |
| collected_at | 系统采集时间 | 系统自动记录 |
| verified_at | 验证完成时间 | 系统自动记录 |
| pushed_at | 推送到用户时间 | 系统自动记录 |
| expires_at | 情报有效期截止 | 按事件类型计算 |

### 7.2 情报默认有效期

| 事件类型 | 有效期 | 过期后处理 |
|:--------|:-----:|:----------|
| 行情异动 | 30分钟 | 失效，不重复推送 |
| 公告 | 1个交易日 | 归档至日报 |
| 行业政策 | 1周 | 归档 |
| 外围市场 | 4小时 | 失效 |
| 技术位 | 1个交易日 | 失效 |

### 7.3 延迟容忍度

| 场景 | 最大容忍延迟 | 超限处理 |
|:----|:----------:|:--------|
| 实时行情 | 15秒 | 标记数据源异常，降级为缓存数据 |
| 公告抓取 | T+1开盘前 | 开盘后公告仍需推送（不过期） |
| 新闻聚合 | 30分钟 | 超过30分钟的新闻标记"非实时" |
| 板块数据 | 2分钟 | 降级显示 |

## 8. 持仓相关性判断

### 8.1 直接相关

- 持仓股票本身的任何事件 → 直接相关
- 持仓股所属行业指数涨跌>2% → 直接相关
- 持仓股十大股东/实际控制人变化 → 直接相关

### 8.2 间接相关

- 同行业/板块其他龙头大幅异动 → 间接相关（可能传导）
- 上下游产业链重大变化 → 间接相关

## 9. 动态异动阈值

### 9.1 价格异动

不是固定5%，而是按个股历史波动计算：

| 级别 | 定义 | 对应幅度（第一版固定值）|
|:----|:-----|:---------------------|
| 常规波动 | 个股60日平均日内波动以内 | 不触发 |
| ⚠️ 关注 | 超过60日均波幅1.5倍 | 亨通≈4.5% / 巨石≈5% / 华工≈5% |
| 🚨 异常 | 超过60日均波幅3倍 | 亨通≈9% / 巨石≈10% / 华工≈10% |

> 第一版使用固定阈值：单票涨跌>4%触发关注，>7%触发异常。后续接入60频数据后改为动态计算。

### 9.2 量能异动

| 指标 | 关注阈值 | 异常阈值 |
|:----|:-------:|:-------:|
| 量比 | >2.0 或 <0.4 | >4.0 |
| 成交量突增 | 同日比前5日均量>150% | >300% |
| 换手率 | >8% | >15% |

### 9.3 板块异动

| 指标 | 关注阈值 |
|:----|:--------|
| 行业指数涨跌 | >3% 或 <-3% |
| 行业成交量 | 前日200%以上 |
| 龙头股异动 | 行业市值前3异动>5% |

### 9.4 公告事件触发

| 事件类型 | 是否触发 | 推送级别 |
|:--------|:-------:|:--------:|
| 业绩预告（大幅变化>50%） | ✅ | P0 |
| 重组/停牌/复牌 | ✅ | P0 |
| 减持/增持公告 | ✅ | P1 |
| 重大合同（占营收>10%） | ✅ | P1 |
| 股权激励/分红方案 | ✅ | P2 |
| 常规年报/季报发布 | ✅ | P1 |
| 变更审计机构/会计政策 | ✅ | P2 |
| 交易所问询/监管函 | ✅ | P0 |
| 一般性新闻 | P2/P3 | 取决于与持仓相关性 |

## 10. 情报优先级与推送规则

### 10.1 四级优先级

| 级别 | 标签 | 推送方式 | 当日限额 |
|:----|:----|:--------|:--------:|
| **P0 紧急** | 🚨 | 立即推送微信 | 不限（但应极罕见）|
| **P1 重要** | ⚠️ | 按规则推送 | 盘中≤3条 |
| **P2 关注** | 👀 | 进入观察清单 | 不单独推送 |
| **P3 归档** | 📋 | 只进入日报 | 不推送 |

### 10.2 P0触发条件（满足任一）

1. 持仓股发布停牌/复牌/ST公告
2. 持仓股收到监管处罚/交易所问询函
3. 持仓股发布业绩预告且变化>50%
4. 盘中异动触发🚨级别（超过3倍日均波幅）
5. 持仓股T+1交易受限（涨跌停封死）
6. 持仓股出现重大资产重组公告

### 10.3 P1触发条件（满足任一）

1. 持仓股涨跌>4%（关注阈值）
2. 持仓股量比>2.0或成交量突增>150%
3. 持仓股所在板块涨跌>3%
4. 持仓股发布一般性公告（分红/减持/合同）
5. 候选池标的触发🚨异常阈值
6. 指数盘中跌>2%（全市场风险）

### 10.4 P2触发条件

1. 候选池标的涨跌>4%
2. 行业板块轮动迹象
3. 外围市场变化（隔夜美股>2%）
4. 技术位接近（持仓股接近关键支撑/阻力）

### 10.5 P3触发条件

1. 常规研报
2. 重复或低相关性新闻
3. 昨天的旧新闻今天又被推送

### 10.6 防打扰规则

- **同一标的30分钟内不重复推送同一事件**（除非事件性质变化）
- **盘后不推送行情异动**（已收盘，推送无意义）
- **同一事件的跨源重复投送合并为1条**（标注多个来源）
- **开盘前15分钟（09:15-09:30）不推送**（集合竞价期间不打扰判断）
- **上午推送已满3条P1时，剩余P1转为P2观察**（当日限额）

## 11. 降级、熔断与异常处理

### 11.1 数据源异常降级

| 场景 | 处理 |
|:----|:-----|
| Sina API连续3次超时 | 切换备用Sina接口 |
| 备用接口也失败 | 使用最近一次缓存数据，标记"行情缓存" |
| TrendRadar不可用 | 直接抓取东方财富热榜（借ScrapeGraphAI）|
| 所有行情源不可用 | 进入**安全模式**：不生成任何盘中操作建议 |
| 公告源不可用 | 降级为仅推送行情类内容 |

### 11.2 熔断条件

满足任一熔断条件 → 当日上午/全天不推送任何操作建议：

1. 3个以上行情源同时不可用
2. DB读写错误连续3次
3. 系统时间误差>5分钟（已修复）
4. 账户基线数据超过1个交易日未更新

### 11.3 异常恢复流程

```
检测到异常
  → 标记受影响的服务和时段
  → 记录到data_quality_log
  → 降级处理（使用缓存/关闭对应模块）
  → 每5分钟重试一次
  → 恢复后推送一条"情报服务恢复正常"通知
  → 积压情报按时间顺序处理，但不追溯推送
```

|:-----|:------|

| 是否导致误判 | 改进验证规则 |

## 14. 验收标准

| # | 标准 | 验证方式 |
|:-:|:----|:--------|
| 1 | 持仓股公告在T+1开盘前被系统获取 | 开盘简报包含所有公告 |
| 2 | 盘中异动>4%在2分钟内被识别 | 时间戳差<120秒 |
| 3 | 同一事件在30分钟内不被重复推送 | 日志检查 |
| 4 | 数据源降级时系统不崩溃 | 断开Sina API看Fallback |
| 5 | 非交易日不推送行情信号 | cron检查 |
| 6 | 每条情报至少经过1层验证 | 日志标记 |
| 7 | 行情源全挂时主动进入安全模式 | 熔断日志 |
| 8 | 账户基线过时>1日时主动提示 | 回填提醒 |
