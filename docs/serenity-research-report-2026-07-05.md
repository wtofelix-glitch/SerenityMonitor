## 1. 执行摘要

### 系统定性

SerenityMonitor 是一个**工程调研扎实、功能完整度高的个人量化投研系统雏形**。它覆盖了从数据采集、多因子评分、信号生成、持仓管理、风控到复盘的完整闭环，代码规模约 50,000 行，19 张数据库表，319 个测试用例。

**但系统现在最大的问题不是功能不够，而是系统太聪明、变量太多、决策链太长，但真正可验证的交易内核还不够硬。**

### 核心结论

> **下一阶段的核心目标：把 SerenityMonitor 从"复杂投研系统"压缩成一个"最小可验证交易内核"，再让情报层、LLM、Agent、Sentinel 这些模块围绕它做辅助，而不是直接参与核心买卖。**

**SerenityMonitor 不应该继续变得更复杂，而应该变得更可验证。先把系统从"聪明"变成"可信"，再从"可信"变成"自动"。**

### 三大 P0 行动项

| # | 行动项 | 一句话 | 时间 |
|---|--------|--------|------|
| P0-1 | **A 股可成交性模拟器** | 没有它，所有回测和信号绩效都不可信 | 3-4 周 |
| P0-2 | **决策审计链** | 每一条信号可回放、可归因、可对账 | 2-3 周 |
| P0-3 | **Frozen Baseline 三系统并跑** | 证明自适应不是自嗨 | 持续运行 |

### 最重要的十条建议

1. **冻结交易内核 60–90 天，停止自动权重和阈值漂移。**
2. **先实现 A 股可成交性模拟器，再谈回测收益。**
3. **所有信号写入 decision_audit_log，做到可回放、可归因。**
4. **Frozen Baseline、Adaptive、Equal Weight 三套系统并行。**
5. **LLM / Sentinel / Agent 全部降级为解释层，等消融实验通过再晋级。**
6. **单票仓位上限从 85% 降到 35%，T+1 新买入仓位上限降到 25%。**
7. **用相关性簇和主题暴露替代传统行业集中度。**
8. **信号体系从"分数阈值"升级为"扣费后净期望收益"。**
9. **建立上线门槛和停机条件，防止系统在失效期继续交易。**
10. **自动交易接口放到最后，必须由实盘半自动数据证明后再启动。**

## 2. 第一步：交易内核冻结

### 2.1 为什么必须冻结

当前系统同时运行四套自适应机制（IC 权重自进化、信号阈值自校准、信源权重进化、Conviction 动态阈值），全部在 15 只股票、不到 300 条信号的小样本上"自学习"。四套机制互相叠加，系统行为不可预测。

**在未来 60–90 天内，核心交易链路必须全部冻结。** 这不是永久放弃自适应，而是先建立一个可验证的静态基线，之后再逐模块验证每个自适应机制是否真的创造增量价值。

### 2.2 冻结清单

| 模块 | 冻结前行为 | 冻结后行为 |
|------|-----------|-----------|
| `weight_adjuster.py` | 每日根据 IC 调整 9 维评分权重 | **使用默认固定权重，不做任何调整** |
| `signal_engine.py` SIGNAL_CONFIG | 根据历史胜率周期性重校准阈值 | **使用固定阈值，不做重校准** |
| `sentinel_engine.py` | 信源权重每日自进化 | **权重只记录不生效，不作为评分输入** |
| `conviction_engine.py` | 根据辩论结果动态调整买卖门槛 | **只输出辩论结果，不调整任何阈值** |
| `sentiment_engine.py` LLM 模式 | LLM 情绪分数参与 technical 评分 | **LLM 情绪只进日报，不进核心分数。关键词模式可作为观察信号** |
| `serenity_council.py` | 委员会投票结果影响信号 | **只输出委员会意见，不改变任何信号** |
| `debate_engine.py` | 辩论结论注入评分 | **只输出辩论摘要，不注入评分** |
| `ensemble_voting.py` | 三源融合信号 | **只输出融合结果作为参考，不作为交易依据** |

### 2.3 保留的最小交易内核

冻结后，核心交易链路退化为：

```text
行情数据（Sina/Tencent，含涨跌停/停牌状态）
  → 基础因子（6-8 个去冗余后的独立因子）
  → 固定评分权重（不再调整）
  → 固定信号阈值（不再调整）
  → A 股可成交性检查（T+1 / 涨跌停 / 停牌 / 流动性）
  → 交易成本扣除（佣金+印花税+滑点）
  → 风控仓位（新上限：单票 ≤35%，主题 ≤50%）
  → 人工确认
  → 审计记录（decision_audit_log）
  → 事后归因
```

所有其他模块暂时作为"观察员"运行——继续产生输出，但不参与交易决策。

### 2.4 冻结期间要做什么

- 运行 P0-3 的 Frozen Baseline 三系统并跑
- 运行消融实验，逐个验证被冻结的模块是否有增量贡献
- 积累 decision_audit_log 数据，建立可统计分析的决策样本库
- 积累实盘（半自动）vs 回测的偏差数据

### 2.5 解冻条件

任何一个被冻结的模块要重新进入交易链路，必须同时满足：

- [ ] 消融实验通过：加入该模块后，扣费净收益/Sharpe/Calmar/胜率有统计显著改善
- [ ] 样本外验证通过：在独立的验证集（未参与调参的数据）上表现优于冻结基准
- [ ] Frozen Baseline 对照通过：加入该模块的 Adaptive 版本跑赢 Frozen Baseline ≥8 周
- [ ] 实盘半自动验证通过：在人工确认模式下，实盘信号质量与回测一致

## 3. 三层架构重构

### 3.1 当前问题

很多模块既像研究工具，又像交易信号，又像解释系统。长期看会非常危险——你无法判断一个决策到底是基于可验证的量化信号，还是基于某个 Agent 的主观判断。

### 3.2 三层定义

#### 第一层：交易内核层（Trading Kernel）

**只允许进入实盘建议链路的模块。** 要求：可回测、可复现、可审计、可扣费、可解释、可和 Frozen Baseline 对照。

```text
data_engine              # 数据获取（需多源 fallback）
factor_engine_core       # 6-8 个去冗余后的独立因子
scorer_core              # 固定权重评分
signal_engine_core       # 固定阈值信号生成
market_microstructure    # [新增] A 股可成交性检查
execution_simulator      # [新增] 成交模拟 + 成本计算
risk_manager             # 风控（需降杠杆 + 增加相关性簇）
portfolio                # 仓位管理（需降杠杆）
decision_audit_log       # [新增] 决策审计链
```

#### 第二层：研究实验层（Research Lab）

这些模块可以产生研究结论，但**默认不能直接影响交易**。只有通过消融实验、样本外验证、Frozen Baseline 对照后，才能晋级进入交易内核。

```text
weight_adjuster          # IC 驱动权重调整
factor_ic                # 因子有效性评估
sentinel_engine          # 多信源监控
sentiment_engine (LLM)   # LLM 情绪分析
market_sense             # 市场体制检测
conviction_engine        # 动态阈值
debate_engine            # 策略辩论
serenity_council         # 5-Agent 委员会
ensemble_voting          # 多源融合投票
moat_factor              # 护城河因子
fundamental_engine       # 基本面因子
```

**晋级流程**：

```text
研究实验层 → 消融实验通过 → 样本外验证通过
  → Frozen Baseline 对照通过（≥8 周）
  → 实盘半自动验证通过
  → 晋级至交易内核层
```

#### 第三层：解释与内容层（Insight & Content）

这些模块适合做自媒体内容、复盘、投研输出，**不要让它们直接决定买卖**。

```text
guru_wisdom              # 大师智库
uzi_insight              # UZI 卡位分析
research_engine          # TrendRadar 全网研究
content_pipeline         # 公众号内容发布
daily_report / weekly_review / premarket_brief
```

### 3.3 一句话原则

> **交易层要冷，研究层要活，解释层要丰富。**

## 4. P0-1：A 股可成交性模拟器

> **这是第一优先级。没有它，所有回测和信号绩效都不可信。**

### 4.1 为什么是 P0-1

当前系统的止盈止损、回测引擎、信号绩效统计，全部隐含假设"信号触发就能按计划价格成交"。在 A 股真实交易中，这个假设不成立：

- **T+1 锁定**：当日买入触发止损 → 无法当日执行 → 实际亏损远超止损线
- **涨跌停**：跌停时卖单无法成交 → 连续跌停时止损体系完全失效
- **停牌**：无法交易
- **一字板**：涨停买不到，跌停卖不掉
- **集合竞价跳空**：开盘价与前一交易日收盘价偏差可能很大
- **小盘股容量**：部分 T2/T3 标的日均成交额低，大仓位无法按回测价格执行

### 4.2 新建模块

```text
market_microstructure.py    # A 股微观结构约束检查
execution_simulator.py      # 成交模拟 + 滑点 + 成本
fill_model.py               # 成交概率模型
```

### 4.3 核心接口

```python
class MarketMicrostructure:
    """A 股微观结构约束检查"""

    def can_buy(self, code: str, date: date, price: float,
                quantity: int) -> TradeabilityResult:
        """检查是否可买入。返回是否可买 + 阻塞原因"""
        ...

    def can_sell(self, position: Position, date: date,
                 price: float) -> TradeabilityResult:
        """检查是否可卖出。需检查：
        - T+1 锁定（当日买入不可卖）
        - 跌停状态（跌停封板不可卖）
        - 停牌状态
        - 持仓数量是否足够
        """
        ...

    def is_t1_locked(self, code: str, date: date) -> bool:
        """该标的当日是否有 T+1 锁定的仓位"""
        ...

    def get_limit_status(self, code: str) -> LimitStatus:
        """获取涨跌停状态：正常 / 涨停 / 跌停 / 一字板"""
        ...


class ExecutionSimulator:
    """成交模拟器"""

    def simulate_fill(self, order: Order, bar: Bar,
                      liquidity: LiquidityState) -> FillResult:
        """模拟订单成交。返回：
        - 是否成交
        - 成交价格（含滑点）
        - 成交数量
        - 未成交原因
        - 实际成本（佣金+印花税+过户费+滑点）
        """
        ...

    def estimate_slippage(self, code: str, quantity: int,
                          side: str) -> float:
        """估算滑点（基于日均成交量、盘口深度等）"""
        ...


class FillModel:
    """成交概率模型"""

    def prob_fill_at_limit_up(self, code: str) -> float:
        """涨停板买入成交概率。一字板 → <5%，普通涨停 → 10-30%"""
        ...

    def prob_fill_at_limit_down(self, code: str) -> float:
        """跌停板卖出成交概率。一字板 → <5%，普通跌停 → 10-30%"""
        ...
```

### 4.4 必须覆盖的约束清单

```text
[x] T+1 锁定（当日买入 → 当日不可卖出）
[x] 涨停不可买（尤其是一字板）
[x] 跌停不可卖（尤其是一字板）
[x] 停牌不可交易
[x] 100 股整数手
[x] 佣金（0.025% 双向）
[x] 印花税（0.05% 卖出单向）
[x] 过户费（0.001% 双向）
[x] 滑点（基于流动性的动态估计，默认 0.1%）
[x] 开盘跳空（集合竞价偏差）
[x] 小盘股容量限制（仓位 vs 日均成交额的比例上限）
[x] 冲击成本（大单对价格的推升/打压）
```

### 4.5 对现有系统的改造

1. **回测引擎**：`backtest_engine.py` 在每笔模拟交易前调用 `can_buy`/`can_sell`，不可成交时跳过该笔交易并记录原因
2. **信号绩效**：所有信号绩效从"理论收益"改为"可成交后净收益"。信号绩效表增加 `net_return_1d/5d/20d` 列
3. **自动执行**：`auto_execute.py` 在生成调仓计划时调用可成交性检查，标记不可执行的指令并说明原因
4. **风控**：新增 T+1 锁定仓位的盘中浮亏追踪，次日开盘自动检查止损状态

## 5. P0-2：决策审计链

### 5.1 为什么是 P0-2

没有审计链，你永远无法回答：

- 这笔亏损是模型错了、风控错了、成交滑点了、还是我人工干预了？
- 回测里的这笔交易在实盘中能不能真的成交？
- 自适应系统调整参数后，到底是变好了还是变差了？

### 5.2 decision_audit_log 表

```sql
CREATE TABLE decision_audit_log (
    -- 基础标识
    decision_id         TEXT PRIMARY KEY,          -- UUID
    created_at          TEXT NOT NULL,             -- ISO timestamp
    stock_code          TEXT NOT NULL,

    -- 策略版本（关键：可复现）

    config_hash         TEXT NOT NULL,             -- 配置 SHA-256
    kernel_frozen       INTEGER DEFAULT 1,         -- 是否在交易内核冻结期

    -- 数据快照
    data_snapshot_id    INTEGER,                   -- FK → daily_snapshots
    feature_snapshot_hash TEXT,                    -- 因子值快照哈希

    -- 评分与信号
    score_components_json TEXT,                    -- 各维度分数
    total_score         REAL,
    signal_type         TEXT,                      -- STRONG_BUY / BUY / ... / SELL
    baseline_signal     TEXT,                      -- Frozen Baseline 会给出什么信号

    -- 市场状态
    market_regime       TEXT,                      -- 市场体制
    theme_exposure      REAL,                      -- AI 供应链主题暴露比例
    correlation_cluster TEXT,                      -- 所属相关性簇

    -- 可成交性（关键新增字段）
    t1_locked           INTEGER DEFAULT 0,         -- 是否被 T+1 锁定
    limit_status        TEXT,                      -- 正常 / 涨停 / 跌停 / 停牌
    can_execute         INTEGER DEFAULT 1,         -- 是否可实际执行
    cannot_execute_reason TEXT,                    -- 不可执行原因

    -- 收益预期
    expected_return_gross REAL,                    -- 预期毛收益
    expected_return_net   REAL,                    -- 预期净收益（扣费+滑点）
    expected_cost         REAL,                    -- 预估交易成本

    -- 风控
    risk_checks_json    TEXT,                      -- 风控检查结果
    suggested_position  REAL,                      -- 建议仓位（金额）
    suggested_position_pct REAL,                   -- 建议仓位（%）

    -- 执行
    execution_status    TEXT,                      -- executed / skipped / pending / blocked
    actual_trade_id     INTEGER,                   -- FK → trades
    fill_price          REAL,                      -- 实际成交价
    slippage            REAL,                      -- 滑点（成交价 vs 信号生成时价格）
    actual_position     REAL,                      -- 实际仓位

    -- 人工干预（关键：可归因）
    human_override      INTEGER DEFAULT 0,         -- 是否人工干预
    human_override_reason TEXT,                    -- 干预原因
    operator_notes      TEXT,                      -- 操作备注

    -- 事后结算
    t1_return_net       REAL,                      -- T+1 净收益（扣费后）
    t5_return_net       REAL,                      -- T+5 净收益
    t20_return_net      REAL,                      -- T+20 净收益
    benchmark_return    REAL,                      -- 同期基准收益
    excess_return       REAL,                      -- 超额收益

    -- 归因
    post_mortem_label   TEXT,                      -- 事后归因标签
    post_mortem_detail  TEXT                       -- 归因详情
);
```

### 5.3 关键新增字段说明

相比 v3 的方案，v4 特别强调以下字段：

| 字段 | 为什么关键 |
|------|-----------|
| `strategy_version` + `config_hash` | 没有这两个字段，6 个月后你不知道这条信号是用哪个版本的参数生成的 |
| `baseline_signal` vs `adaptive_signal` | 直接对比冻结基准和自适应系统对同一场景的判断 |
| `signal_divergence` | 两个系统判断不一致时标记，这是发现自适应机制问题的核心线索 |
| `human_override` + `human_override_reason` | 区分"系统判断错误"和"人工干预导致结果差" |
| `expected_return_net` | 信号生成时就要算好扣费后预期收益，用于后续验证 |
| `slippage` | 区分"模型错了"和"成交价格差了" |

## 6. P0-3：Frozen Baseline 三系统并跑

### 6.1 三套系统定义

每天同一批行情输入，三套系统各自生成信号，各自模拟执行，互不干扰：

```text
系统 A — Frozen Baseline（冻结基准）
  ├── 固定权重（初始默认值，永不变）
  ├── 固定阈值（初始值，永不变）
  ├── 无情报层输入
  ├── 无 LLM 情绪
  ├── 无 Sentinel
  ├── 无 Conviction
  └── 同样的可成交性检查 + 交易成本 + 风控约束

系统 B — Adaptive System（当前自适应系统）
  ├── IC 权重自进化
  ├── 信号阈值自校准
  ├── 信源权重自进化
  ├── Conviction 动态阈值
  ├── LLM 情绪
  └── 同样的可成交性检查 + 交易成本 + 风控约束

系统 C — Equal Weight Basket（等权基准）
  ├── 15 只标的等权买入持有
  ├── 每月首个交易日再平衡回等权（避免权重自然漂移导致
  │   "事后看恰好持有了涨得最多的那几只"的失真）
  ├── 再平衡时扣除交易成本（佣金+印花税+滑点）
  └── 设计理由：不做任何再平衡的"买入持有"会在几周后
      自然漂移为涨跌幅度决定的加权组合，不再代表"等权"，
      不适合作为 Frozen Baseline 的硬性停机判据的对比基准
```

## 7. 统计方法论修复

（本节承接 v3 §2 的核心分析，此处概述关键发现和修复方案。完整的统计方法论审计见 v3 报告。）

### 7.1 核心问题回顾

1. **阈值校准的 train-test 泄漏**：272 条信号 → 调阈值 → 同一批数据验证 → 必然"变好"
2. **四套自适应系统叠加**：IC 权重 + 阈值 + 信源权重 + Conviction，全部在小样本上日更
3. **回测缺少简单基准**：没有 vs 等权持有、vs 沪深 300
4. **参数 ~61 个 vs 有效独立观测 ~750 个**：比例不算极端，但自适应交互产生隐式自由度

### 7.2 修复方案

| 问题 | 修复 | 实施阶段 |
|------|------|---------|
| Train-test 泄漏 | 所有参数调整强制时间切分，验证集必须独立 | P0-3（Frozen Baseline 本质上就是验证集） |
| 自适应叠加 | 冻结 60-90 天，之后逐模块解冻 | §2 交易内核冻结 |
| 缺基准对比 | 回测必须展示 vs 三个基准的超额收益 | Phase 2 |
| 参数过多 | 因子去冗余（|r|>0.7 合并），ICIR 替代简单 IC | Phase 2 |
| 权重日更追噪音 | 权重调整降频至周更，设最小样本量 ≥50 | Phase 2 |
| **多重比较膨胀** | **消融实验的 7 个模块各自用 α=0.05 做显著性检验 → 至少一个被误判为有效的概率 ~30%。用 Bonferroni 校正（α/7≈0.007）或 Benjamini-Hochberg FDR 控制** | Phase 3 消融实验 |
| **股票池后见之明** | **T1-T3 标的如果是 CPO/AI 主题走强后才纳入候选池，所有下游分析都在被污染的样本空间里打转。需回溯入池时间线 + 做"主题启动前就已存在的候选范围"的反事实回测** | Phase 3 消融实验前置步骤 |

### 7.3 多重比较校正

系统在 Phase 3 消融实验中需要检验 7 个模块（moat / sentiment / sentinel / LLM / conviction / market_sense / council）各自是否有统计显著的增量贡献。

**问题**：如果 7 个模块各自独立地用 α=0.05 做显著性检验，至少一个模块被误判为"有显著增量贡献"（即假阳性）的累积概率约为：

```text
P(至少一个假阳性) = 1 - (1 - 0.05)^7 ≈ 0.30 = 30%
```

这意味着即使所有模块都完全无效，也有 ~30% 的概率至少有一个被误判为有效。

**修复**：在 Phase 3 消融实验的判定环节使用多重比较校正：

| 方法 | 严格度 | 适用场景 |
|------|--------|---------|
| **Bonferroni 校正** | 最严格（α/7 ≈ 0.007） | 假阳性代价极高时使用（如决定模块是否进入交易内核） |
| **Benjamini-Hochberg FDR** | 适中（控制假阳性比例 ≤5%） | 研究层模块排序时使用（允许一定假阳性，控制整体比例） |

**建议**：
- 模块晋级至交易内核 → 使用 Bonferroni 校正（α/7）
- 模块在研究层内排序优先级 → 使用 BH-FDR
- 不得让 Ablation-1 到 Ablation-7 各自独立地用 5% 阈值判断"是否显著"

### 7.4 股票池后见之明审计

这是从 v3 到 v4 一直未被触及的更上游偏差来源：**即使交易内核、可成交性模拟器、Frozen Baseline 全部做对，如果标的池本身的选择包含了"事后诸葛亮"，所有下游的严谨设计都是在一个已经被污染的样本空间里打转。**

#### 需要回溯的关键问题

1. T1-T3 这 10 只 CPO/AI 供应链标的，是在主题走强**之后**才被纳入候选池，还是在此之前就已经在池子里？
2. 候选池的扩充时间线：最初 10 只（BUILD_PLAN 中的 Tier 1-3）→ 后来加入 T4 防御组合 → 后来又加入紫光股份(000938)——每次扩充的具体时间点和触发原因是什么？

#### 反事实回测

在 Phase 3 消融实验中，增加一个前置步骤：

```text
步骤 1：回溯每只标的的入池日期
步骤 2：构建"主题启动前就已存在的候选范围"（假设 CPO/AI 主题在 2024 年底-2025 年初启动）
步骤 3：用这个固定候选范围重新跑一遍完整回测（相同的因子、相同的评分、相同的信号规则）
步骤 4：对比"当前池"和"固定池"的回测结果
步骤 5：差异归因——超额收益中，多少来自"选对了池"，多少来自"池内的择时能力"
```

#### 判定

```text
如果"固定池"的回测结果显著弱于"当前池"：
  → 策略收益中相当一部分来自主题走强后的池扩充（Beta），
     而非池内的选股/择时能力（Alpha）
  → 在向外部展示系统有效性时，必须显式剥离"选池效应"

如果"固定池"的回测结果没有显著弱于"当前池"：
  → 池扩充没有引入实质性后见之明偏差
  → 可以将此结论写入系统文档
```

这一条不会阻塞 Phase 1-2 的执行，但必须在 Phase 3 消融实验开始前完成，作为消融实验的前置步骤，与因子去冗余并行进行。

## 9. 信号体系升级：分数阈值 → 净期望收益

### 9.1 当前信号体系的问题

v3 报告已暴露一个关键矛盾：**HOLD 区间（50-60 分）的历史表现优于 STRONG_BUY 和 BUY。** 这说明"总分越高 → 收益越高"的单调性假设不成立。

当前信号生成的逻辑本质是：

```python
# 当前逻辑（有问题）
if score >= 74:
    signal = "STRONG_BUY"
elif score >= 66:
    signal = "BUY"
```

这个逻辑的问题是：**它只问"分数高不高"，不问"赚不赚钱"。**

### 9.2 新逻辑：净期望收益

```python
# 建议逻辑
def generate_signal(code, scores, market_state, position):
    # 1. 计算扣费后预期净收益
    expected_net_return = estimate_expected_return(
        code, scores, market_state, horizon_days=5
    ) - estimate_trading_cost(code, position)

    # 2. 检查可成交性
    tradeability = microstructure.can_buy(code, date, price)

    # 3. 检查风险约束
    risk_ok = risk_manager.check_all(position, expected_net_return)

    # 4. 信号生成
    if (expected_net_return > cost_of_capital + risk_premium
        and tradeability.is_executable
        and risk_ok
        and theme_exposure < THEME_LIMIT):
        signal = "BUY"
    elif expected_net_return < -risk_threshold:
        signal = "SELL"
    else:
        signal = "HOLD"

    return signal, expected_net_return, tradeability, risk_ok
```

### 9.3 信号等级重新定义

| 信号 | 新定义 |
|------|--------|
| **STRONG_BUY** | 预期净收益高 AND 回撤风险低 AND 可成交性好 AND 组合暴露允许 |
| **BUY** | 预期净收益为正 AND 风险可接受 AND 可成交 |
| **CAUTION_BUY** | 预期净收益为正 BUT 成交性/主题暴露/波动率有瑕疵 |
| **HOLD** | 没有足够净收益优势（扣费后预期收益不足以覆盖风险补偿） |
| **SELL** | 预期净收益转负 OR 风险约束触发 OR 止损触发 |

### 9.4 核心新增字段

每个信号必须携带：

```text
expected_net_return     # 信号生成时就计算好的扣费后预期收益
expected_cost           # 预估交易成本
tradeability_status     # 是否可成交 + 阻塞原因
theme_exposure_after    # 成交后的主题暴露比例
```

事后结算时，对比 `expected_net_return` 和 `actual_net_return`，这个偏差本身就是最重要的绩效指标。

### 12.1 不要删除情报层，但要从"交易信号"改为"研究假设"

Sentinel、Guru、LLM、UZI、辩论引擎是系统特色，也适合做自媒体内容和投研输出。但它们当前不适合直接作为交易权重。

### 12.2 各模块的新定位

| 模块 | 新定位 | 输出形式 |
|------|--------|---------|
| **Sentinel** | 发现市场叙事变化 | "本周 CPO 主题正面信号增强，n 个独立信源确认" |
| **Guru Wisdom** | 提供长期框架 | "当前估值水平处于巴菲特/芒格框架的哪个区间" |
| **LLM 情绪** | 总结新闻和风险 | "今日主要风险提示：xxx" |
| **UZI** | 解释 AI 供应链卡位 | "该标的在供应链中处于 X 环节，壁垒等级 Y" |
| **Debate Engine** | 生成多空假设 | "看多理由：A/B/C；看空理由：D/E/F" |
| **Council** | 输出复盘意见 | "本周信号回顾：胜率变化/最大失误/改进方向" |

### 12.3 假设生成与验证流程

**每一个情报层产生的信号，必须先转成可验证假设，才能在研究层中追踪。**

```text
假设生成：
  "Sentinel 检测到 CPO 主题正面信号增强"

假设：
  "CPO 主题正面信号增强后，T1 标的（光迅/华工）未来 5 日超额收益为正"

验证（事后）：
  过去 N 次同类 Sentinel 信号中，
  扣费后 T+5 平均超额收益是否 > 0？
  统计显著性如何？

结论：
  显著 → 该信号可作为研究层因子，进入消融实验队列
  不显著 → 该信号仅保留在解释层
```

### 12.4 信源治理专项

```text
1. 信源权重加入人工复核层：
   - 自动计算建议权重
   - 人工确认后才生效
   - 单次权重变化 > ±20% → 强制人工复核

2. 信源独立性检查：
   - 多个信源同时给出相同方向信号 → 检查是否来自同一信息源
   - 同一研报被多个博主转发 → 共振 ≠ 独立验证 → 信号打折

3. 原始观测完整保存：
   - 不做 500 字截断
   - 被删除/修改的观测标记为"数据完整性异常"
   - 异常观测的信源降低信任权重

4. 利益冲突标记：
   - 博主推荐标的与其公开持仓的重合度
   - 历史"喊单后出货"模式检测
```

### 13.3 停机条件（策略层面）

以下条件触发**观察模式**（只记录信号，不新增仓位，只允许减仓）：

```text
条件 1：连续 4 周 Adaptive 净收益跑输 Equal Weight Basket
条件 2：最大回撤超过预设值（建议：-15%）
条件 3：连续 3 次止损触发后，同主题标的的相关性仍 > 0.7
条件 4：数据源质量异常（价格缺失/数据时点异常）连续出现 ≥2 次
条件 5：decision_audit_log 记录缺失（信号生成了但审计记录未写入）
条件 6：回测收益与实盘收益偏差持续扩大（连续 4 周偏差 > 2%/周）
条件 7：人工干预比例超过 30%（说明系统信号不被信任，或信号质量有问题）
```

以下条件触发**紧急停机**（清空所有 T1-T3 仓位，仅保留 T4 底仓）：

```text
条件 1：组合回撤超过 -20%
条件 2：核心数据源（Sina API）连续 3 天不可用
条件 3：检测到系统性未来函数泄漏
条件 4：AI 供应链主题叙事出现根本性反转（如英伟达宣布放弃 CPO 路线）
```

## 14. 实施路线图（终版）

### 核心原则：先冻结，再验证，最后自动化。

```
Phase 1 ── 交易内核冻结 + A 股微观结构 (3-4 周) ── P0
Phase 2 ── 决策审计链 + Frozen Baseline 上线 (2-3 周) ── P0
Phase 3 ── 统计方法论修复 + 消融实验 (4-6 周) ── P0/P1
Phase 4 ── 小资金半自动实盘验证 (12 周) ── P1
Phase 5 ── 模块晋级 + 自动交易接口 (条件触发)
```

### Phase 1：交易内核冻结 + A 股微观结构（P0，3-4 周）

```
Week 1-2: 交易内核冻结
  ├── 执行 §2.2 的冻结清单
  ├── 权重/阈值/信源权重/Conviction 全部冻结
  ├── LLM 情绪退出核心评分
  ├── Agent 委员会退出交易许可
  └── 保留最小交易内核（§2.3）

Week 2-4: A 股微观结构建模
  ├── market_microstructure.py（可成交性检查）
  ├── execution_simulator.py（成交模拟 + 成本）
  ├── fill_model.py（成交概率）
  ├── T+1 状态机 + 次日开盘自动止损检查
  ├── 涨跌停/停牌/一字板处理
  └── 新增测试: test_market_microstructure / test_t1_lock / test_limit_up_down / test_no_lookahead
```

### Phase 2：决策审计链 + Frozen Baseline 上线（P0，2-3 周）

```
Week 5-6: 决策审计链
  ├── decision_audit_log 表创建 + 写入逻辑
  ├── 信号生成时保存完整上下文（含 baseline_signal vs adaptive_signal）
  ├── 事后结算自动回填 t1/t5/t20 net return
  └── 新增测试: test_audit_replay

Week 6-7: Frozen Baseline 初始部署
  ├── Frozen Baseline 版本建立（§6.1 系统 A）
  ├── Equal Weight Basket 系统建立（§6.1 系统 C，含每月再平衡）
  ├── 三系统并行运行框架搭建
  ├── 看板集成三系统对比视图
  └── 每周自动生成对比报告

⚠️ 时序对齐说明：
  Frozen Baseline 此时用的是当前 14 个因子的版本（称"Frozen v1"）。
  Phase 3 Week 8-10 因子去冗余完成后，Frozen Baseline 的因子集会更新
  （称"Frozen v2"），此时 §6.3 的 8/12 周判定时钟**重置**，从 v2 上线后
  重新开始计时。Frozen v1 阶段的对比数据作为参考，不用于硬性判定。
  这是为了避免用已知要被替换的旧因子版本消耗宝贵的判定窗口。
```

### Phase 3：统计方法论修复 + 消融实验（P0/P1，4-6 周）

```
Week 8-9: 股票池后见之明审计 + 因子审计（并行）
  ├── [前置] 回溯 15 只标的入池时间线（§7.4）
  ├── [前置] "主题启动前固定候选范围"反事实回测
  ├── [前置] 分离"选池效应"和"池内择时能力"

  └── Frozen Baseline 在因子去冗余后更新为 v2 → 重置判定时钟

Week 10-12: 回测升级 + 消融实验
  ├── 回测引擎升级为事件驱动（§8）
  ├── 回测加入三大基准对比
  ├── 交易成本显式建模 + 税后净收益列

  ├── [关键] 判定时使用 Bonferroni 校正（α/7）

  └── 结论：哪些可以进入研究层，哪些永远留在解释层
```

## 附录 B：术语表

| 术语 | 说明 |
|------|------|
| **交易内核** | 最小可验证的交易链路：数据→因子→评分→信号→可成交性→风控→执行→审计。除此之外的模块默认不参与交易决策 |
| **Frozen Baseline** | 不做任何自适应调整的固定规则版本，用于检验自适应机制是否真正有效 |
| **Equal Weight Basket** | 15 只标的等权买入持有，不调仓，最简策略基准 |
| **可成交性模拟器** | 模拟 T+1/涨跌停/停牌/流动性/成本等 A 股微观约束下订单能否成交 |
| **相关性簇** | 基于近 60 日收益相关矩阵识别出的高度同向波动标的群，替代传统行业分类衡量真实分散度 |
| **净期望收益** | 扣除了佣金+印花税+滑点+冲击成本后的预期收益，是判断是否开仓的核心依据 |
| **假设生成器** | 情报层的新定位：Sentinel/Guru/LLM/Debate 产生可验证的假设，而非直接产生交易信号 |
| **观察模式** | 停机条件触发后的状态：只记录信号、不新增仓位、只允许减仓 |
